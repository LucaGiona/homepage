1. ÜBERBLICK
========================================================================
Das Projekt ist eine mehrseitige, statische Homepage (HTML + CSS +
Vanilla-JS, kein Framework, kein Build-Tool), gehostet auf Netlify.
Inhaltlich: Startseite, About, Services, Galerie, Zertifikate, Drinks
(mit LocalStorage-CRUD), Impressum, Datenschutz.

Der Ansatz "einfaches, framework-loses Setup" ist für dieses Projekt
grundsätzlich richtig. Der aktuelle Zustand wirkt aber wie ein
Zwischenstand: mehrere Seiten haben kaputte Pfade/Links, Platzhalter-
Inhalte und Copy-Paste-Reste, die vor einem "fertigen" Release noch
bereinigt werden sollten.

========================================================================
2. POSITIVE PUNKTE
========================================================================

- Sauberes semantisches HTML: header/main/footer/nav/section/article
  werden weitgehend korrekt eingesetzt (z. B. index.html, about.html).

- Guter Ansatz bei Barrierefreiheit: aria-expanded, aria-controls,
  aria-live="polite", role="list", aria-label, aria-describedby und
  <fieldset>/<legend> werden im Drinks-Formular (html/drinks.html,
  js/addDrink.js) durchdacht eingesetzt. Das ist deutlich über dem
  Niveau eines typischen Einsteiger-Projekts.

- Responsive Bilder: html/galerie.html nutzt <picture> mit mehreren
  <source srcset> (web_small/medium/large, WebP + JPG-Fallback) –
  performance- und browserkompatibel gelöst.

- Wiederverwendbare Templates: nav.html und footer.html werden per
  fetch() zentral eingebunden (js/nav.js) statt in jeder Seite
  dupliziert zu werden – guter Ansatz gegen Redundanz ohne Build-Tool.

- LocalStorage-CRUD (js/addDrink.js) ist funktional vollständig:
  Anlegen, Bearbeiten, Löschen, Einzel- und Sammel-Löschen, inkl.
  Event-Delegation auf dem Cards-Container statt einzelner Listener
  pro Karte – das ist ein solides, nicht-triviales Pattern.

- Filter-/Sortierlogik (js/drinkFilter.js) ist klar strukturiert,
  arbeitet über data-Attribute statt Klassen-Toggles, und die
  deutsche, numerische Sortierung (localeCompare mit "de") ist ein
  durchdachtes Detail.

- Rechtliches vorhanden: Impressum und Datenschutzerklärung sind
  eingebunden – für ein Projekt mit Klarnamen/Kontakt in Deutschland
  relevant und oft vergessen.

- .gitignore ist sinnvoll konfiguriert (macOS-Systemdateien, private
  Text-/Ideen-Ordner werden korrekt ausgeschlossen).

- Zertifikats-Seite (js/certifications.js) hat einen netten Kniff:
  eine Lookup-Tabelle formatiert Dateinamen zu sauberen Titeln
  (z. B. "css" -> "CSS", "openai" -> "OpenAI") statt hartcodierter
  Titel-Liste.

--- A) Kaputte Links & Pfade (funktionale Bugs) ---------------------

1. html/drinks.html:6 und html/galerie.html:6
   Beide referenzieren <link rel="stylesheet" href="/style.css">.
   Die Datei liegt aber unter /css/style.css. Auf diesen zwei Seiten
   wird also KEIN Stylesheet geladen (nur Browser-Default-Styles).

2. templates/nav.html:6-8
   Links zu "projekte.html" und "blog.html" sind relativ (kein
   führendes "/") UND die Zieldateien existieren im Projekt gar
   nicht. Das betrifft die Hauptnavigation auf JEDER Seite -> 404
   auf jeder Seite über das Navigationsmenü. Der Linktext "test" für
   den Blog-Eintrag ist zusätzlich ein sichtbarer Platzhalter.

3. html/services.html:45
   Link auf "/html/projects.html" – Datei existiert nicht (das
   Galerie-/Projekt-Pendant heißt "galerie.html").

4. html/galerie.html:53
   Tippfehler im Pfad: ".../green_water_ducks02.webpp" (doppeltes p).
   Dieses Bild lädt dadurch nie das große WebP – stiller Fallback-Bug.

--- B) Ungültiges / inkonsistentes HTML -------------------------------

5. html/services.html
   Der komplette <body>-Tag fehlt (nach </head> folgt direkt <header>
   ohne öffnendes <body>). Ungültiges HTML, Browser reparieren das
   automatisch, aber es sollte korrigiert werden.

6. html/services.html
   Als einzige Unterseite hat sie keinen <footer> mit den
   Datenschutz-/Impressum-Links, die alle anderen Seiten haben –
   inkonsistent.

7. Sprachattribut uneinheitlich: index.html, about.html,
   certifications.html, galerie.html und impressum.html deklarieren
   lang="en", obwohl der gesamte sichtbare Text Deutsch ist. Nur
   html/drinks.html hat korrekt lang="de". Relevant für Screenreader
   (falsche Ausspracheregeln) und SEO.

--- C) Copy-Paste-Reste / Platzhalter-Inhalte ------------------------

8. index.html:9 -> <title>test</title>
   Placeholder-Titel, der es bis in den Haupteinstieg geschafft hat.

9. html/about.html:10 -> <title>Certifacts</title>
   Falscher, von certifications.html kopierter Titel.

10. html/about.html:9 lädt <script src="/js/certifications.js">,
    obwohl auf der About-Seite weder #pngList noch #pngViewer
    existieren – totes Skript, unnötiger Request.

11. html/galerie.html enthält produktiv mehrere Platzhalterbilder von
    picsum.photos und placehold.co (Zeilen ~60-77) inkl. Test-Labels
    ("picsum (placehoder)", Tippfehler "placehoder"). Wirkt wie
    Debug-/Testinhalt, der live ist.

12. index.html:44-46 -> Abschnitt "Some very good drinks" ohne
    weiteren Inhalt – unfertiger Platzhaltertext auf der Startseite.

13. html/galerie.html: Alt-Texte sind für unterschiedliche Bilder
    identisch bzw. falsch, z. B. die "ducks"-Bilder tragen denselben
    Alt-Text wie die reinen Wasserbilder ("...See mit Algen bedeckt
    und Baumstämme" statt einer Beschreibung der Enten).

--- D) CSS -------------------------------------------------------------

14. css/style.css:7-10
    summary { color: aqua; background-color: pink; }
    Wirkt wie Test-/Debug-Styling (grelle, nicht zum Rest passende
    Farben) und sollte durch ein durchdachtes Design ersetzt werden.

15. css/style.css:58-60
    .visually-hidden { display: none; }
    Das ist ein klassischer Accessibility-Anti-Pattern: display:none
    entfernt den Inhalt auch aus dem Accessibility-Tree, d. h. die
    ganzen sorgfältig gesetzten <span class="visually-hidden"> in
    drinks.html/addDrink.js (die Screenreadern zusätzlichen Kontext
    geben sollen) werden AUCH von Screenreadern nicht vorgelesen.
    Der Zweck der Klasse wird dadurch komplett unterlaufen. Richtige
    Umsetzung: die bekannte "sr-only"-Kombination aus position:
    absolute; width:1px; height:1px; overflow:hidden; clip-path:
    inset(50%); white-space:nowrap;

16. Insgesamt ist style.css mit 61 Zeilen sehr minimal für ein
    Projekt, das laut README schon deployed ist – es gibt kein
    durchgängiges Layout-/Typografie-/Farbsystem, keine Responsive-
    Breakpoints außerhalb der <picture>-Elemente, kein einheitliches
    Spacing. Der Großteil der Seite läuft aktuell im Browser-
    Standardlook.

--- E) JavaScript ------------------------------------------------------

17. js/addDrink.js (addDrinkToDOM, updateCardInDOM):
    Nutzereingaben (drink.name, ingredients, recipe, preparation,
    garnish, tip) werden ungefiltert per Template-String in
    innerHTML/insertAdjacentHTML eingesetzt. Da die Daten aus
    LocalStorage stammen (Single-User, kein Server, kein Sharing),
    ist das Risiko aktuell gering, aber es ist eine Self-XSS-Lücke:
    Eingabe von z. B. <img src=x onerror=...> im Namensfeld würde
    ausgeführt. Sollte spätestens vor einem Ausbau (z. B. Sync über
    ein Backend) über textContent oder eine Escaping-Hilfsfunktion
    behoben werden.

18. js/script.js:16 – Kommentar "alle 3 Sekunden wechseln", tatsächliches
    Intervall ist aber 7000 ms. Veralteter/irreführender Kommentar.

19. Die 9 Drink-Karten in html/drinks.html sind vollständig hartcodiertes
    HTML (ca. 250 Zeilen), während neue/eigene Drinks über addDrink.js
    als JS-Objekte im LocalStorage verwaltet und dynamisch gerendert
    werden. Es existieren damit zwei parallele Datenmodelle für
    dieselbe Sache (Drink-Karten) – jede Änderung an der Kartenstruktur
    muss an zwei Stellen gepflegt werden. Empfehlung: die 9 Start-
    Drinks als JS/JSON-Array definieren und mit derselben Render-
    Funktion wie die Custom-Drinks erzeugen.

--- F) SEO / Metadaten / Projektorganisation --------------------------

20. Keine einzige Seite hat eine <meta name="description">, Open-Graph-
    Tags oder ein Favicon – für eine öffentlich verlinkte Homepage
    (siehe README, Presseartikel-Links) ein klarer Lücke bei SEO und
    Social-Sharing-Vorschau.

21. Kein package.json, kein Linting/Formatting (ESLint/Prettier), keine
    Tests, kein CI. Bei einem so kleinen Projekt ist ein volles Setup
    nicht zwingend nötig, aber zumindest HTML-Validierung und ein
    einfacher Link-Checker in CI würden die oben genannten Bugs (kaputte
    Pfade, fehlender <body>) automatisch abfangen.

22. Zertifikate liegen redundant in zwei Formaten/Ordnern
    (assets/certifications/*.pdf und assets/pngs/*.png) ohne
    erkennbaren automatisierten Prozess dazwischen – manuelle
    Doppelpflege bei jedem neuen Zertifikat.

23. README.md ist sehr knapp: keine Ordnerstruktur-Erklärung, keine
    Setup-/Lokal-Start-Anleitung (z. B. "wie starte ich lokal einen
    Server"), keine Hinweise für zukünftige Mitwirkende.

24. assets/portraits/ liegt aktuell ungetrackt im Arbeitsverzeichnis
    (siehe `git status`) und wird in keiner HTML-Datei referenziert –
    entweder ein in Arbeit befindliches Feature (Portrait auf
    Startseite?) oder ein vergessenes Asset. Sollte bewusst
    eingebunden oder aus dem Ordner entfernt werden.

6. VORSCHLAG: WORKFLOW
========================================================================

BRANCHING
  - main = immer deploybarer Stand (Netlify deployt automatisch von
    main).
  - Für jede Änderung einen kurzlebigen Branch:
      fix/<kurzbeschreibung>      z. B. fix/css-pfad-drinks
      feat/<kurzbeschreibung>     z. B. feat/portrait-startseite
      chore/<kurzbeschreibung>    z. B. chore/readme-setup
  - Pull Request gegen main, auch als Einzelperson – so bleibt eine
    Historie mit Beschreibung pro Änderung, und der CI-Check (siehe
    unten) läuft vor dem Merge statt danach.

ISSUES & LABELS
  Empfohlenes Label-Set:
    bug            – funktional kaputt (Links, Pfade, Layout bricht)
    content        – Text-/Bild-Inhalte, Platzhalter ersetzen
    accessibility  – a11y-spezifische Punkte
    seo            – Meta-Tags, Sprache, Discoverability
    security       – z. B. XSS-Absicherung
    refactor / tech-debt – Code-Struktur, ohne sichtbares Verhalten
    enhancement    – neue, gewünschte Funktionalität
    chore          – Wartung, Doku, CI, Tooling
    question       – Klärungsbedarf vor Umsetzung
    priority:high/medium/low – ergänzend zu jedem Issue

PROJECT BOARD (GitHub Projects, einfaches Kanban)
  Spalten: Backlog -> To Do -> In Progress -> In Review -> Done
  - Neue Issues landen in Backlog.
  - Vor jeder Arbeitssession 1-3 Issues nach "To Do" ziehen
    (bewusst kleine Batches, da Solo-Projekt).
  - Ein Issue = ein Branch = ein PR = eine Karte, die durchs Board
    wandert.

COMMIT-KONVENTION
  Kurzformat wie in der bisherigen Historie schon teilweise genutzt,
  aber vereinheitlicht nach Conventional Commits:
    fix: css pfad auf drinks.html korrigiert
    feat: portrait auf startseite eingebunden
    chore: readme setup-anleitung ergänzt
    refactor: drink-daten in js-array ausgelagert
  Vorteil: automatisch lesbare Historie, Basis für ein optionales
  CHANGELOG.

DEFINITION OF DONE (pro Issue/PR)
  - Betroffene Seite(n) lokal im Browser geprüft (nicht nur Code
    gelesen).
  - Keine kaputten internen Links (manuell oder via Link-Checker).
  - HTML bleibt valide (kein fehlender <body>/<main> etc.).
  - Bei a11y-relevanten Änderungen: kurzer Screenreader-Check.

CI (GitHub Actions, minimal & passend zur Projektgröße)
  Workflow bei jedem Pull Request:
    1. html-validate über alle *.html-Dateien
    2. linkinator (oder ähnlicher Link-Checker) gegen interne Links
    3. optional: Lighthouse-CI für Performance/SEO/A11y-Score als
       Info (nicht blockierend am Anfang)
  Das fängt genau die Fehlerklasse ab, die diese Review dominiert
  (kaputte Pfade, fehlendes <body>, defekte Bildlinks).

RELEASE / DEPLOYMENT
  - Bleibt wie bisher: Netlify deployt automatisch bei Push/Merge auf
    main. Kein Änderungsbedarf, nur sicherstellen, dass PRs statt
    Direct-Pushes auf main der Normalfall werden, damit CI vor dem
    Live-Gang greift.

VORSCHLAG REIHENFOLGE (nächste Schritte)
  1. Alle "priority:high"-Issues aus Abschnitt 5 (kaputte Links/CSS/
     HTML) in einem gemeinsamen PR "fix: kaputte Links und Pfade
     beheben" beheben – größter sichtbarer Nutzen, kleinster Aufwand.
  2. Accessibility-Fix (.visually-hidden) + lang-Attribute – zweiter
     PR, da inhaltlich zusammengehörig (beides a11y).
  3. Content-Cleanup (Platzhalterbilder/-texte, Titles) – dritter PR.
  4. Danach mittelfristig: Design-System in style.css, Drink-Daten-
     Refactor, CI-Setup.
